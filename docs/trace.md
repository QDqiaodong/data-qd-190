# 混放筹码批次溯源 `showdown-trace`

`showdown-trace` 把一批需要单独核销的“标记筹码”混入普通筹码后，沿整段 v1 牌谱追踪它们**可能**的去向。录像只记录谁投入多少、每个池付给谁多少，无法辨认哪一枚实物属于待核销批次，因此本命令不认定任何一枚实物的归属，也不指定先花哪一批；它枚举符合全部 v1 数量约束的**整条可行流向**，给出盘点组在“同一条完整流向中同时成立”的数量凭证，并核对一份逐人清点能否由整段牌谱产生。

它不做转账、不更新 `showdown-ledger` 账本或 `showdown-corpus` 样本库，也不改变六个旧命令（`showdown-pots`、`showdown-ledger`、`showdown-audit`、`showdown-reconcile`、`showdown-corpus`、`showdown-replay`）的输入、输出、退出码与契约。所有金额都是整数筹码，完全离线，仅用 Python 标准库。

## 命令行

```sh
showdown-trace --source request.json --output run/trace.json
```

成功时原子新建 `--output`（不覆盖已有目标，含符号链接），并在 stdout 打印摘要，例如：

```json
{"counted_possible": true, "groups": 6, "players": 4}
```

结构错误、无法结算的手、破坏库存约束的手或读写失败：stderr 说明原因，退出 2，不发部分报告，也不覆盖已有输出。相同输入给出稳定结果；重排对象键、查询组或组内 ID 不影响报告。

## 输入

严格 JSON 对象，必填 `hands, groups`，可选 `counted`，并须恰好有 `initial` 或 `checkpoint` 之一。

```json
{
  "initial": {
    "balances": {"A": 1, "B": 1, "C": 1, "D": 1},
    "marked":   {"A": 1, "B": 0, "C": 0, "D": 1}
  },
  "hands": [ /* 0..1000 份完整 v1 输入，按时间排列 */ ],
  "groups": [
    {"id": "gA", "players": ["A"]},
    {"id": "gAB", "players": ["A", "B"]}
  ],
  "counted": {"A": 1, "B": 1, "C": 0, "D": 0}
}
```

- `initial.balances` 与 `initial.marked` 使用完全相同的 2..6 个玩家 ID（v1 字符规则 `[A-Za-z0-9_:-]{1,64}`，各自无重复）。期初总量为 0..10⁹ 的整数；标记数量为 0..该人总量的整数。中途不增减筹码、不换名册；期末单人总量可以超过 10⁹。身份始终按 ID，不按座位。
- `hands` 是 0..1000 份按时间排列的完整 v1 单手输入，每手由项目现有 v1 规则（`showdown_pots.service.process`）校验并结算。参加者必须在名册内；缺席者持有量不动。任何人的毛投入（v1 的 `committed`）超过该手期初其持有的总量，即使本手结束会拿到退回或派奖，也按坏牌谱拒绝（退出 2）。
- `groups` 为 0..64 项 `{id, players}`；组 ID 用 v1 ID 规则且批内唯一，`players` 是名册中非空且不重复的 ID 列表。
- `counted` 若给出，必须是覆盖全名册一次的对象，值为 0..6×10⁹ 的整数。结构不符（漏人、多人、类型或范围错误）按结构错误退出 2；结构正确但数量不可同时实现时仅令 `counted_possible` 为 false，不影响正常报告。

## 输出

成功发布 `{balances, groups, counted_possible, checkpoint}`。

- `balances`：全名册期末总量（v1 逐手净结算累加；全局筹码守恒）。
- `groups`：按查询 ID 的 ASCII 顺序，每项 `{id, marked_min, marked_max, unmarked_min}`。
  - `marked_min`/`marked_max` 是在**同一条完整流向**中对该组求和后、跨全部可行流向的最小值和最大值。
  - `unmarked_min = 组内期末总量 − marked_max`。
  - 这些只是数量凭证，不能据此认出任何一枚实物。
- `counted_possible`：仅当清点中的全部数量能在同一条可行流向中同时出现时为 true；未提供 `counted` 时为 null。
- `checkpoint`：见下节。

### 为什么不能把个人最大值相加

标记筹码在全桌守恒（期初共 M 枚就永远是 M 枚）。可行的期末持有向量是一个整体多面体，不是每人独立区间的笛卡尔积：每个人单独可能达到的最大值通常争用同一批标记来源，无法同时取到。例如对照班次（A 与 C 平局、B 与 D 平局）后续 A 独赢的牌谱里，A 单独的标记范围是 [0,2]、B 是 [0,0]，而组 [A,B] 的 `marked_max` 只有 2，绝不是 2+0 之外再做任何独立相加；更一般地，任何子集 S 的同时持有上界都由整段历史的网络割约束决定，本命令逐子集直接计算，不做独立区间求和。

清点的判断同理：必须存在**一条**完整流向同时满足全部人的清点值；把不同流向里各自可行的数字拼起来不算可行。

## 筹码流向口径（追踪所枚举的世界）

每一手按 v1 结算出贡献层、匹配池与未匹配退回后，标记筹码在以下约束内流动：

1. 玩家从手头任意选择满足数量的筹码，投入自己参与的各贡献层；每个匹配池里该玩家投入的数量就是 v1 该池 `to_inclusive − from_exclusive`，弃牌也照付。每枚筹码一手里只走一条去路。
2. 未投入部分始终留在手里。未匹配退回（`uncalled_returns`）是该玩家毛投入中单独划出的一段，原样回到本人，不进任何匹配池、不随池重分配。
3. 每个匹配池单独混放：向各获奖者交付的总量严格等于 v1 该池的整数 `awards`（含并列余筹，余筹按 v1 固定座次发放，本命令直接采用 v1 结果而不做等分近似）。在满足数量时池内标记筹码可任意分配，但一个池的余额或标记不能挪给另一个池。
4. 每人把留存、退回、各池所得合在一起带到下一手。

盘点口径是满足上述约束的**全部整条流向**。同一玩家从不同池拿到的份额、不同玩家之间的份额可能争用同一来源；本命令不任取一条流向当真值，也不把多条流向的结果拼成一份清点。

## 检查点与班次交接

各班次按时间先后交接：后续班次只拿得到前一班次的检查点和本班牌谱，拿不到历史源文件或逐手记录。查询对象在盘点时才指定，出检查点时不知道下一班会查谁，因此检查点不携带任何查询参数。

### 检查点格式（version 1）

下面是班次一（A-B 平局、C-D 平局，期初 A、D 各有 1 枚标记）后续完 A、B 赢家手后，命令实际发布的检查点：

```json
{
  "v": 1,
  "ids": ["A", "B", "C", "D"],
  "t": {"A": 2, "B": 0, "C": 1, "D": 1},
  "m": 2,
  "u": [0, 1, 0, 1, 1, 2, 1, 2, 1, 2, 1, 2, 1, 2, 1, 2]
}
```

- `v`：格式版本，当前固定为 1。未知版本拒绝。
- `ids`：排序后的全名册 ID；`t`：每人当前筹码总量；`m`：全桌标记筹码守恒总量（本例始终为 2）。
- `u`：长度 2^n（n 为 2..6）的数组，按名册位掩码（bit i 对应 `ids[i]`，所以掩码 1 是 A、掩码 2 是 B）索引。`u[mask]` 是**截至当前停点的全部历史**中，掩码对应子集所能同时持有的标记筹码最大数量，即该子集的容量上界。它是时间展开筹码流动网络的多汇最大流函数，单调且满足次模性，`u[0]=0`、`u[全掩码]=m`。本例 B 已无筹码（`t.B=0`），所以凡只落在 B 身上的容量（如 `u[2]=0`）都为 0。

### 必须保留的历史事实，以及为什么这样就够了

后续班次要回答“任意一组人在同一条流向中至少/至多持有多少标记”，等价于在“历史网络 + 本班各手”的合并流动网络上求多汇最大流。最大流/最小割定理保证：历史网络对边界（当前各人手牌）的全部可行约束，恰好由子集容量函数 `u` 完整刻画——只保留 `u`（连同当前总量 `t` 与守恒量 `m`、名册 `ids`）就足以对任何后续手和任何查询子集复算相同答案，无需保留牌面、逐手记录、座位历史或具体分摊。每处理一手，就用本手的浅网络（自留/退回弧与互相独立的池节点）按多面体最大流最小割公式把 `u` 整体更新一次；因此检查点可以再次交接，接续结果与从开局一次读入同样牌谱完全一致。

所有运算都作用在聚合数量上，复杂度只与名册人数（≤6，子集 ≤64）、手数（≤1000）和池数有关，与筹码面额无关：不按每一枚筹码、也不按每一种整数分摊逐个遍历，10⁹ 与 1 的计算量相同。

### 2048 字节交接栏

教室交接栏只收检查点对象本身按 UTF-8、键排序、无分隔空白和末尾换行、非 ASCII 不转义的 JSON 编码（即 `json.dumps(checkpoint, ensure_ascii=False, sort_keys=True, separators=(",", ":"))` 的 UTF-8 字节数）。6 人名册、最长 64 字符合法 ID、各总量取到合法上限时仍低于 2048 字节（实测最坏情形约 1.6 KB）。命令在生成检查点时即按此编码核算，超限按输入错误退出 2。检查点不依赖源文件、历史牌谱、上次查询、缓存或后台进程，也不允许用外部文件引用转移数据；它不携带牌面、逐手记录或座位历史。

### 信任边界与损坏检测

信任同事确实使用本命令生成交接数据，不要求签名，也不证明历史真实性。但以下情况按结构错误拒绝（退出 2）：未知版本、缺字段或多字段、类型/范围错误、ID 不合法或不排序、容量表长度不对、`u[0]≠0`、`u[全掩码]≠m`、容量超过对应子集的实际筹码总量、单调性或次模性被破坏、`m` 超过全桌总量。

### 接续请求

把检查点对象原样放入下次请求的 `checkpoint` 字段（不要重新排序或改写），并提供本班 `hands`、本次 `groups`（可选 `counted`）：

```json
{
  "checkpoint": { … 原样复制上一份输出里的 checkpoint 对象 … },
  "hands": [ /* 本班牌谱 */ ],
  "groups": [{"id": "gA", "players": ["A"]}]
}
```

接续请求不得再带 `initial`。接续后可再次交接；输出里的新检查点与从开局直跑相同牌谱产生的检查点一致。查询与清点值都不改变交接状态。

## 复算验收示例

### 示例 1：两种配对班次的区分

A、B、C、D 期初各持 1，标记分别为 1、0、0、1。每手指定两人各投 1、均不弃牌；平局用公共牌 `Tc Jc Qc Kc`、`Ac`，两人底牌 `2d 3d` 与 `4d 5d`，各收回 1 枚。

- 班次一：A-B 平局，再 C-D 平局。
- 对照班次：A-C 平局，再 B-D 平局。

两份班次的期末总量相同（每人仍为 1），每人各自的标记范围也都是 [0,1]。但只有对照班次，清点 `{"A":1,"B":1,"C":0,"D":0}` 可能成立（班次一的 A-B 池只含 1 枚标记，不可能让 A、B 同时各持 1 枚标记）。

分别只带两份检查点，在新进程续同一手：A、B 各投 1，公共牌 `2c 3d 4h 8s 9c`，A 底牌 `5c 6c`、B 底牌 `Kh Ks`，A 独得两枚。两边 A 都持有 2 枚；班次一 A 的标记范围恰为 [1,1]（普通筹码至少 1），对照班次为 [0,2]（普通筹码至少 0）。从开局直跑两条路线得到相同的查询与清点判断。

### 示例 2：池隔离、退回隔离与并列余筹

- 用仓库 `fixtures/input.json` 作为一手，期初总量恰好等于各自毛投入（ace 100、king 50、straight 20、fold 70），只有 king 的 50 枚全部有标记。期末标记数量必须恰好为 straight 20、ace 30，其余人为 0：king 的标记进不了它未参与的第 3 池，ace 被退回的 30 枚是未匹配退回、不是任何池的贡献。只把 ace 期初总量减为 99（毛投入 100 超持有）必须拒绝。
- 三人并列例（按钮座位 0）：A、B 坐 0、1，采用示例 1 的平局牌面，第三人坐 2 弃牌且底牌为空；三人各持 1、各投 1、全部有标记。v1 把 3 枚池按固定座次发成 B 得 2、A 得 1，因此 B 的标记数恰为 2、A 恰为 1，不能用等分比例代替 v1 实发。

### 示例 3：长班次、删除源文件与大额

把示例 1 班次一的两手重复 500 次（共 1000 手）作为一班，删除源文件后仅凭检查点续 A、B 的赢家手，仍得班次一结果（A 标记恰为 1）。把各人期初总量与两次平局的单人投入放大为 10⁹、A 和 D 的期初持有全部为标记，续局 A、B 各投入 10⁹ 时，A 的标记数仍恰为 10⁹、普通筹码至少 10⁹；检查点真实编码长度可直接按上节方式核算并断言不超过 2048 字节。整个计算不随面额变慢。

## 边界

本命令只在 v1 牌谱模型上追踪混放标记筹码的数量可行性，不认定实物归属、不指定花费顺序、不做转账，也不复核下注街次合法性（那是 `showdown-replay` 的职责）。输出是教学盘点凭证，不是实际赌场或财务核销认证。离线回归测试见 `tests/test_trace.py`。
